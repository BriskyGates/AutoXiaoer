# Auto小二（AutoXiaoer）技术演进与架构评析

> 面向架构评审、路线图讨论与二创决策。与 `PROJECT_ARCHITECTURE.zh-CN.md`、`PROMPTS_ANALYSIS.zh-CN.md`、`multi-model-agent-research.md` 互补：本文侧重**问题归纳、迭代优先级、ReAct 之外的代理范式**及主观技术判断。  
> **文档版本**：基于仓库当前架构与源码阅读整理；若实现变更，请以代码为准同步修订本文。

---

## 1. 产品与技术定位（一句话）

**在 Android 上运行的「视觉 + 语言」智能体**：`LLMAgent`（文本模型）负责高层拆解与调度，近似 **ReAct（Think → Act → Observe）**；`PhoneAgent`（视觉模型）在 **截图 → 推理 → 动作 DSL → Shizuku 执行** 闭环中落地操作。触发源含手动、定时、通知、ClawBot 等，由 `TaskExecutionManager` 统一编排。

与业界 Midscene（Planning / Insight / Locate）、Mobile-Agent 多角色、Hi-Agent 高低层拆分等方案在**思想上一致**：用分工应对「长序列、噪声 UI、每步成本高」的移动端特点。

## 2. 当前实现的主要问题与风险

以下按**对稳定性 / 成本 / 可维护性的影响**大致排序。

### 2.1 契约不一致：规划层「思考」标签与解析器

- **现象**：`LLMAgentPrompts` 要求模型使用**标签名** `redacted_thinking` 的成对标签包裹思考过程；`LLMAgent.extractThinking()` 却调用 `extractBlock(rawContent, "think")`，只会查找**标签名**为 `think` 的成对标签（`extractBlock` 用 `"<$tag>"` 拼接）。二者**不一致**，多数情况下依赖「**第一个 `<action>` 之前**的整段」作为思考内容的兜底。
- **连带问题**：`extractThinking` 的 KDoc 若写「优先解析 `redacted_thinking`」而实现仍用 `"think"`，则文档与代码易继续漂移。
- **实际影响**：常见依赖「`<action>` 之前整段作为兜底」展示思考，**换模型或改模板时**易出现展示异常或后续若依赖 thinking 文本的逻辑漂移。
- **建议**：以**单一真源**统一标签名（或支持可配置的多标签列表），并增加**固定样例的解析回归测试**。

**相关代码**：`app/.../agent/LLMAgent.kt`（`extractThinking` / `extractBlock`）、`config/LLMAgentPrompts.kt`。

### 2.2 动作协议偏「字符串 DSL」，健壮性有天花板

- **执行层**：`do(...)` / `finish(...)` + 括号平衡等解析逻辑。
- **规划层**：`<action>` 内 JSON，`type` 与 `when` 分支强绑定。
- **风险**：模型多符号、少括号、混用引号即可导致空 action、误解析；调试成本高。
- **建议**：在供应商能力允许时，优先 **JSON Schema / tool（function）calling** 约束输出；失败时携带校验错误自动重试。执行层每步含截图，**协议硬化 ROI 往往高于单纯换大模型**。

### 2.3 安全与合规：软边界为主

- 敏感界面黑屏、截图出域、支付等场景**无硬件级沙箱**，依赖 Prompt 与产品规则。
- **建议**：危险操作与指定包名结合**系统级二次确认**（用户显式手势）；自动化范围**白名单**；可选打码/降采样策略（需评估对 grounding 的影响）。

### 2.4 成本与延迟：双端点 API + 高频多模态

- Phone 与 LLM **各一套** OpenAI 兼容配置；长任务下 **HTTP 轮次 × 每步全屏图** 主导成本与延迟。
- **建议**：ROI 裁剪或差分触发大模型、本地轻量「是否达成上一步意图」判别、复杂任务再启用分层双调用等（详见第 4 节）。

### 2.5 可维护性：超长 System Prompt 与场景规则堆叠

- 全局规则过多时，模型难以全部遵守；电商、社交等**宜场景注入**，而非全部写入默认 System（参见 `multi-model-agent-research.md` 中「动态规则」思路）。
- 已有 **规划层 `preGeneratedTexts` 注入执行层** 的跨层协作，可沿同思路扩展「场景规则块」。

### 2.6 测试与线上差距

- 单元 / 属性测试覆盖解析与坐标等模块，但线上失败常来自 **真实模型输出分布 + SSE + 机型截图时序**。
- **建议**：脱敏「黄金样本」回归、新 Prompt 灰度仅日志对比、可选录制回放管线。

### 2.7 系统依赖：Shizuku

- **能力**：非 Root 下获得较强 Shell 能力。  
- **代价**：安装与授权门槛高，属**架构级取舍**；若面向更广人群，需产品层面评估多轨方案（维护成本显著上升）。

## 3. 推荐迭代路线（按优先级）

| 阶段 | 内容 | 说明 |
|------|------|------|
| P0 | 统一提示词 ↔ 解析契约 + 测试 | 小改动、高收益，避免后续迭代建立在不稳定解析上 |
| P1 | 执行层结构化输出 + 失败 Reflection | 降空 action、误触；Reflection 对列表/触控误差往往比单纯换模型划算 |
| P2 | 显式「计划」数据结构 + 条件重规划 | 从「每轮像 ReAct」演进为可控 plan + replan |
| P3 | 多专职 Agent 或双 VLM 分层 | 仅当核心场景需要冲高成功率或差异化付费时再上 |

## 4. 除 ReAct 外，适用于手机 / GUI 自动化的常见范式

ReAct 适合**短上下文、工具边界清晰**的任务。移动端 GUI 往往**部分可观测、噪声大、步数长、单步昂贵**，业界常见演进如下（可与现有双 Agent 组合，而非非此即彼）。

### 4.1 Plan-and-Execute（规划与执行分离 + 动态重规划）

- **要点**：Planner 产出**结构化计划**（步骤、依赖、完成条件）；Executor 逐步执行；环境变化时**局部或整体 replan**。
- **参考**：如 [Plan-and-Act: Improving Planning of Agents for Long-Horizon Tasks](https://arxiv.org/html/2503.09572v2) 等对长程规划的讨论。
- **与 Auto 小二**：已有 LLM + Phone 分工，可增强**计划对象持久化**与**明确 replan 触发条件**，减少仅靠自然语言 Observation 的模糊性。

### 4.2 Reflexion / Critic（执行后批判与纠错）

- **要点**：每步或每子任务后评估「意图是否达成」；失败则生成简短纠错策略再执行。
- **与业界**：Mobile-Agent-v3 中的 Reflector 等角色与此同构。
- **评价**：在 Android **坐标漂移、列表懒加载**场景下，**性价比通常较高**。

### 4.3 分层视觉（子目标 + Grounding）

- **要点**：高层输出子目标（自然语言或结构化）；低层专做坐标 / 控件级动作。
- **参考**：Hi-Agent 等「高层推理 + 低层动作」分层工作（参见 `multi-model-agent-research.md` 引用）。
- **评价**：适合复杂跨 App；延迟与成本上升，宜**按需开关**。

### 4.4 多 Agent 专职化（Manager + Worker + Notetaker + …）

- **要点**：角色拆分、职责单一；部分工作引入持久记忆或经验条（如 Mobile-Agent-E 等「自进化」思路）。
- **参考**：[Mobile-Agent-E: Self-Evolving Mobile Assistant for Complex Tasks](https://arxiv.org/html/2501.11733v1)。
- **评价**：**上限高、工程与联调成本高**；建议在有明确标杆任务集或商业化场景后再投入。

### 4.5 Tree-of-Thoughts（多候选再择优）

- **要点**：在歧义大处分叉多条短计划，评分后执行。
- **评价**：手机端每步多分支会**成倍增加调用成本**；适合**关键分叉**而非全程展开。

### 4.6 状态机 / EFSM 引导（SPlanner 等思路）

- **要点**：将头部 App 交互抽象为有限状态或扩展有限状态机，LLM 主要做转移选择而非从零推理整个应用逻辑。
- **评价**：对**微信、系统设置、电商主路径**等极有效；长尾 App 需录制或众包补状态，否则覆盖难。

### 4.7 Observe 通道工程化（强化「观察」而非换范式名）

- **要点**：除截图外，引入 **Shell 返回码、当前包名 / Activity、可得的 Toast 等结构化信号**，降低纯视觉幻觉。
- **评价**：常被视为小改动，但对**稳定性**帮助大，可与 ReAct / Plan-Execute 任意组合。

### 4.8 其他文献向思路（检索摘要）

- **D-PoT 等动态规划思路**：强调随反馈调整规划，缓解长对话下 ReAct 退化（具体指标与设定见原论文）。
- **SPlanner（EFSM 等）**：在 AndroidWorld 类基准上报告相对纯 VLM 的显著提升（见相关预印本与社区解读）。
